# 2pres_workflow_v1 — 通用开发工作流

> ⚠️ **未经项目磨合的通用版本（v1.5）**。设计经过推敲，实跑暴露的问题已修复（见 [CHANGELOG.md](CHANGELOG.md)），但尚未在多个真实项目中验证过，接口与提示词可能随迭代变动。欢迎 fork 后按自己项目改造。

## 这是什么

面向 [ZCode](https://zcode.dev)（v0.17+，dynamic workflows）的多 agent 开发工作流：接到一个自包含任务后，自动走完

```
规划（拆解出五段式任务书，开工前读禁止再犯清单）
  → 独立审查计划（换模型互审，意见分"必须改/建议"，≤2轮）
  → [可选] 人工确认计划
  → 按难度分档派工（依赖一满足立即开工；上游失败自动跳过下游）
  → 卡住请教导师（裁决落盘决策日志）
  → 每个任务做完立刻由便宜模型核对它的回执（和其他任务同时进行）
  → [可选] 脚本执行项目验收命令，没过直接修
  → Opus 终验三态（pass / fail / pass+改进项）
  → fail 则修复循环（≤N轮）
  → 交付报告
```

### quick 模式（方向已谈定时用）

在主会话里把解决方向聊清楚后，传 `mode=quick`，把定好的方向写进 `task`：

```
Opus 任务分派员：读禁止再犯清单、记录开工基线、清空上次的决策日志，
                 把方向拆成 1~5 个任务，每个任务写好完成标准
  → 按依赖派全新执行者（互不依赖的同时跑）
  → 卡住就问 Opus 导师，不限次数
  → 每个任务做完由便宜模型核对回执
  → [可选] 脚本执行项目验收命令
  → Opus 终验，不通过由 Opus 修复工程师修
```

和完整模式的区别：跳过 GLM 规划师和 Opus 计划审查，改由 Opus 一步拆完任务；不写 PLAN.md、tasks.md；不支持人工确认计划。方向还没定、或任务大到需要先审计划的，用完整模式。

设计原则：**每个任务派全新执行者，只喂自包含任务书**；主流程不碰代码只调度；**能用命令判定的就用命令判定**，不信 agent 自述；**全部状态落盘 markdown**（工作区根的 `.planning/`：PLAN.md、tasks.md、decision-log.md、backlog.md、logs/），跨会话可交接，不怕上下文压缩。

## 模型分档（默认值，可整表替换）

| 角色 | 模型 |
|---|---|
| 规划师（full 模式） | GLM-5.3 |
| 任务分派员（quick 模式） | 强模型开关 `STRONG`，默认 Claude Opus 5.5 |
| 执行者·simple | DeepSeek v4.1 Flash |
| 执行者·medium | GLM-5.3 |
| 执行者·hard | GLM-5.3（卡住可请教导师） |
| 回执核对员 | DeepSeek v4.1 Flash（纯机械对照，每个任务一个） |
| 导师 / 计划审查员 / 验收员 / 修复工程师 | 强模型开关 `STRONG`，默认 Claude Opus 5.5 |

**Opus 额度用完怎么办**：脚本里有一行 `const STRONG = OPUS;`，只有上表里标了 `STRONG` 的角色用它。运行中 Opus 额度用完（运行被停下或长时间卡住）时，把这行改成 `const STRONG = GLM;`，再用 AmendWorkflow 指向改好的文件续跑，已完成的步骤按缓存规则复用，不用从头跑。工作流脚本本身发现不了额度用完（模型报错不会交给脚本），所以这一步需要人或主会话来做。

脚本内的模型 ID 是作者环境（`new-provider*`）的，**fork 时务必改成你自己的模型 ID**。

## 安装

把 `dev-loop.dwf.ts` 复制到 ZCode 的 workflow 目录之一，并改名为 `2pres_workflow_v1.dwf.ts`（文件名就是调用时的名字）：

- 全局：`~/.zcode/workflows/`（所有项目可用）
- 项目级：`<项目>/.zcode/workflows/`

之后在会话中按名调用：`CreateWorkflow saved: { name: "2pres_workflow_v1" }`。**会话要开在项目根目录**，所有计划和日志都会落在它下面的 `.planning/`，验收命令也在这个目录下执行。

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `task` | 必填 | 自包含任务描述：做什么、交付什么、涉及哪些文件；quick 模式写已谈定的方向 |
| `mode` | `full` | `quick` = 方向已谈定，Opus 直接拆任务分派执行者 |
| `human_checkpoints` | `false` | 仅 full 模式：`true` = 计划审完暂停，带决策清单等人工拍板 |
| `max_fix_rounds` | `5` | 修复轮数上限（1-10），验收命令没过和验收员判 fail 共用 |
| `accept_cmd` | 空 | 项目自带的验收命令，如 `npm test`、`./scripts/verify.sh` |
| `accept_markers` | 空 | 命令输出里必须出现的固定文字，多个用分号分隔 |

## 项目验收命令（accept_cmd）

项目有现成的检查脚本时，强烈建议传 `accept_cmd`。它比模型判断更硬，也更省 Opus：

- 终验前由脚本在会话工作目录下用 Git Bash 执行，最长 60 分钟，完整输出写到 `.planning/logs/accept.log`
- 退出码非 0，或 `accept_markers` 里任一标记没出现，直接派修复工程师，修完脚本重跑，不经过验收员
- 通过后验收员不再跑这条命令，只判断它覆盖不到的问题；验收员判 fail 后的每轮修复也会重跑它
- 修复轮数用完还没过，运行停下，结论里写明退出码和缺失的标记

例：`accept_cmd = ./scripts/verify-app-layer.sh`，`accept_markers = RELEASE_PIN_SYNC_OK;APP_LAYER_VERIFY_OK`。

## 禁止再犯清单

规划师开工前会读一份"禁止再犯清单"，计划审查员拿它检查计划，重犯任何一条都算必改问题。清单里每条都来自真实运行。路径在脚本的 `LESSONS_PATH` 常量，默认是作者知识库的 `docs/工作流禁止再犯清单.md`；文件不存在时两个角色会跳过。新踩的坑直接追加到这份文件，不用改脚本。

## 定制（fork）

脚本内所有可定制位置都有 `[FORK]` 注释标记：

1. 模型分派表与强模型开关（换模型 / 加档位）
2. `.planning/` 目录约定（换落盘路径与文件名）
3. 禁止再犯清单的路径
4. 验收命令用的 shell 路径与超时（Linux/mac 改成 `bash`）
5. 修复工程师、验收员档位
6. 任务调度策略（默认：依赖满足即开工、上游失败跳过下游、成环时按顺序串行）

复杂项目：复制本文件改名（避免同名抢占触发词）→ 按注释逐处适配 → 改 frontmatter 的 description / whenToUse。

## 已知局限

- v1.1 完整跑通过一次；v1.2 到 v1.5 的改动是根据那次数据和外部经验做的，**改完后还没跑过**
- quick 模式的任务没有经过独立审查，拆得好不好全看 Opus 分派员一次判断；导师答疑设了 30 次保险上限，防止同一个问题无限循环
- hard 档执行者换成 GLM 后，难任务的完成质量可能比 Opus 差，靠导师答疑和 Opus 终验兜底，效果待实跑确认
- 额度用完不能自动降级，需要人改 `STRONG` 开关后续跑；换模型后缓存能否命中尚未实测
- 会话要开在项目根目录：`.planning/` 和验收命令都以会话的工作目录为准
- 验收命令写死了 Windows 上 Git Bash 的安装路径，其他系统要改
- 卡住超过 20 分钟才报警、改了任务内容后缓存全部作废，这两点是 ZCode 平台机制，脚本改不了
- 没传 `accept_cmd` 时终验只靠 Opus 判断，成本不低
- 非 git 仓库会自动降级：记录不到基线 commit 时，以文件快照（行数/字节）做增量基准
- 执行者用的模型推理档没有单独下调，token 消耗主要靠提示词纪律控制
