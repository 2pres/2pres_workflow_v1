# 2pres_workflow_v1 — dev-loop 通用开发工作流

> ⚠️ **未经项目磨合的通用版本（v1.3）**。设计经过推敲，两次实跑暴露的问题已修复（见下方「更新记录」），但尚未在多个真实项目中验证过，接口与提示词可能随迭代变动。欢迎 fork 后按自己项目改造。

## 这是什么

面向 [ZCode](https://zcode.dev)（v0.17+，dynamic workflows）的多 agent 开发工作流：接到一个自包含任务后，自动走完

```
规划（拆解出五段式任务书）
  → 独立审查计划（换模型互审，意见分"必须改/建议"，≤2轮）
  → [可选] 人工确认计划
  → 按难度分档派工（依赖一满足立即开工；上游失败自动跳过下游）
  → 卡住请教导师（裁决落盘决策日志）
  → 每个任务做完立刻由便宜模型核对它的回执（和其他任务同时进行）
  → Opus 终验三态（pass / fail / pass+改进项）
  → fail 则修复循环（≤N轮）
  → 交付报告
```

设计原则：**每个任务派全新执行者，只喂自包含任务书**；主流程不碰代码只调度；**全部状态落盘 markdown**（`.planning/` 目录：PLAN.md、tasks.md、decision-log.md、backlog.md），跨会话可交接，不怕上下文压缩。

## 模型分档（默认值，可整表替换）

| 角色 | 模型 |
|---|---|
| 规划师 | GLM-5.3 |
| 计划审查员 | Claude Opus 5.5（换模型防同款盲区） |
| 执行者·simple | DeepSeek v4.1 Flash |
| 执行者·medium | GLM-5.3 |
| 执行者·hard | GLM-5.3（卡住可请教 Opus 导师） |
| 回执核对员 | DeepSeek v4.1 Flash（纯机械对照，每个任务一个） |
| 导师 / 计划审查员 / 验收员 / 修复工程师 | 强模型开关 `STRONG`，默认 Claude Opus 5.5 |

**Opus 额度用完怎么办**：脚本里有一行 `const STRONG = OPUS;`，只有上表最后一行的四个角色用它。运行中 Opus 额度用完（运行被停下或长时间卡住）时，把这行改成 `const STRONG = GLM;`，再用 AmendWorkflow 指向改好的文件续跑，已完成的步骤按缓存规则复用，不用从头跑。工作流脚本本身发现不了额度用完（模型报错不会交给脚本），所以这一步需要人或主会话来做。

脚本内的模型 ID 是作者环境（`new-provider*`）的，**fork 时务必改成你自己的模型 ID**。

## 安装

把 `dev-loop.dwf.ts` 复制到 ZCode 的 workflow 目录之一：

- 全局：`~/.zcode/workflows/`（所有项目可用）
- 项目级：`<项目>/.zcode/workflows/`

之后在会话中按名调用：`CreateWorkflow saved: { name: "dev-loop" }`。**会话要开在项目根目录**，所有计划和日志都会落在它下面的 `.planning/`。

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `task` | 必填 | 自包含任务描述：做什么、交付什么、涉及哪些文件 |
| `mode` | `full` | `quick` = 小任务直通（跳过规划审查，单执行者+验收） |
| `human_checkpoints` | `false` | `true` = 计划审完暂停，带决策清单等人工拍板 |
| `max_fix_rounds` | `5` | 验收 fail 后修复循环上限（1-10） |
| `tier` | `medium` | 仅 quick 模式：执行者档位 |

## 定制（fork）

脚本内所有可定制位置都有 `[FORK]` 注释标记：

1. 模型分派表（换模型 / 加档位）
2. `.planning/` 目录约定（换落盘路径与文件名）
3. 修复工程师档位
4. 任务调度策略（默认：依赖满足即开工、上游失败跳过下游、成环时按顺序串行）

复杂项目：复制本文件改名（避免同名抢占触发词）→ 按注释逐处适配 → 改 frontmatter 的 description / whenToUse。

## 更新记录

**v1.3**（缩短耗时、降低 Opus 额度风险）

v1.1 那次实跑里 Opus 一共用了约 3010 万 token（全程 58%），其中 2920 万是 5 个 hard 档执行者用的，审查、验收加起来才 90 万；Opus 额度用完后运行只会空等重试，脚本没有任何应对。另外回执核对员要等所有任务做完才开工。针对这些改了：

- hard 档执行者从 Opus 改为 GLM-5.3，Opus 只留给计划审查员、导师、验收员、修复工程师四个角色
- 这四个角色统一读一个强模型开关 `STRONG`，额度用完时改一行即可切到 GLM 续跑（见上方「Opus 额度用完怎么办」）
- 回执核对员改为每个任务做完立刻派一个去核对，和其他任务同时进行；下游任务不等上游的核对。核对不再单独占一段时间
- 用 EvalWorkflowSnippet 模拟验证过调度：下游在上游核对结束前就开工、上游失败时下游被跳过、核对结果一条不漏

**v1.2**（根据 v1.1 第一次完整跑通的数据优化）

那次运行共 229 分钟、5160 万 token，验收通过，但暴露了这些问题：会话目录和项目目录各长出一套 `.planning/`，修复任务去错的目录找报告，判成"文件不存在"，漏修了两个缺陷；回执核对员把回归全量重跑了一遍，一个环节用了 105 分钟；规划师自己又排了"终验"任务，回归一共跑了三遍；两个修复任务约 1600 万 token，只改了 194 行代码；回执里的数字有 10 处和实际不符。针对这些改了：

- 档案根固定为工作区根下的 `.planning/`，规划完脚本检查 PLAN.md、tasks.md 确实在那里，不在就让规划师改正一次，再不在就报错停下；tasks.md 里对不上本次任务的（上一次运行留下的旧文件），也会让规划师覆盖重写
- 执行者和修复工程师开工前先 `ls` 确认点名的输入文件都在，找不到必须如实上报，不许当成"已处置"
- 回执核对员只读日志和文件做对账，禁止重跑测试；回归日志统一写到 `.planning/logs/`
- 规划师被告知工作流自带核对和终验，不再排终验类任务；回归只在开头跑基线、在终验跑终态，各一次
- 执行者、修复工程师、核对员、验收员都加了读文件纪律：先 grep 定位，再按行读，单次不超过 120 行
- 回执里的任何数量必须来自命令输出（`grep -c`、`wc -l` 等），禁止模型自己数

**v1.1**（根据首跑实测数据优化）

首跑：一次真实任务共花 1690 万 token，其中一个执行者独占 1246 万；计划审查两轮都没给出"通过"；验收员这一个环节挂住，整条流程没跑完。针对这些改了：

- 执行者加省力纪律：每条验收命令只跑一次、长输出只看摘要、发现在重复检查就停下；完成标准每个任务不超过 6 条
- 调度从"按批等齐"改为"依赖满足即开工"；上游失败或卡住时下游自动跳过（看板新增"跳过"列）；依赖成环时按顺序串行（原来实际是全并行，与日志不符）
- 验收拆两层：Flash 核对员先逐条对照回执，Opus 只查实不一致之处并抽查关键命令
- 计划审查意见分 blockers / suggestions，只有 blockers 阻塞开工
- 规划师勘察范围收窄到与任务直接相关的部分
- quick 模式执行者开工前先自列 ≤5 条完成标准

**v1**：首版，含拆分守则（任务数最少化、同文件任务禁排 3+ 串行长链）。

## 已知局限（诚实清单）

- v1.1 完整跑通过一次；v1.2、v1.3 的改动是根据那次数据做的，**改完后还没跑过**
- hard 档执行者换成 GLM 后，难任务的完成质量可能比 Opus 差，靠导师答疑和 Opus 终验兜底，效果待实跑确认
- 额度用完不能自动降级，需要人改 `STRONG` 开关后续跑；换模型后缓存能否命中尚未实测
- 会话要开在项目根目录：`.planning/` 落在会话的工作目录下，开在别处档案就会落在别处
- 卡住超过 20 分钟才报警、改了任务内容后缓存全部作废，这两点是 ZCode 平台机制，脚本改不了
- 终验仍由 Opus 做，成本不低；小任务请用 `mode=quick`
- 非 git 仓库会自动降级：记录不到基线 commit 时，以文件快照（行数/字节）做增量基准
- 执行者用的模型推理档没有单独下调，token 消耗主要靠提示词纪律控制
