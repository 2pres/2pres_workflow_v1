# 2pres_workflow_v1 — dev-loop 通用开发工作流

> ⚠️ **未经项目磨合的通用版本（v1）**。设计经过推敲、首跑暴露的问题已修复（过度拆分 → 已内置拆分守则），但尚未在多个真实项目中验证过，接口与提示词可能随迭代变动。欢迎 fork 后按自己项目改造。

## 这是什么

面向 [ZCode](https://zcode.dev)（v0.17+，dynamic workflows）的多 agent 开发工作流：接到一个自包含任务后，自动走完

```
规划（拆解出五段式任务书）
  → 独立审查计划（换模型互审，≤2轮）
  → [可选] 人工确认计划
  → 按难度分档逐任务派工（无依赖并行、有依赖串行）
  → 卡住请教导师（裁决落盘决策日志）
  → 三态验收（pass / fail / pass+改进项）
  → fail 则修复循环（≤N轮）
  → 交付报告
```

设计原则：**每个任务派全新执行者，只喂自包含任务书**；主流程不碰代码只调度；**全部状态落盘 markdown**（`.planning/` 目录：PLAN.md、tasks.md、decision-log.md、backlog.md），跨会话可交接，不怕上下文压缩。

## 模型分档（默认值，可整表替换）

| 角色 | 模型 |
|---|---|
| 规划师 | GLM-5.3 |
| 计划审查员 | Claude Opus 5.5（换模型防同款盲区） |
| 执行者·simple | DeepSeek v4.1 Flash |
| 执行者·medium | GLM-5.3 |
| 执行者·hard | Claude Opus 5.5 |
| 导师 / 验收员 / 修复工程师 | Claude Opus 5.5 |

脚本内的模型 ID 是作者环境（`new-provider*`）的，**fork 时务必改成你自己的模型 ID**。

## 安装

把 `dev-loop.dwf.ts` 复制到 ZCode 的 workflow 目录之一：

- 全局：`~/.zcode/workflows/`（所有项目可用）
- 项目级：`<项目>/.zcode/workflows/`

之后在会话中按名调用：`CreateWorkflow saved: { name: "dev-loop" }`。

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `task` | 必填 | 自包含任务描述：做什么、交付什么、涉及哪些文件 |
| `mode` | `full` | `quick` = 小任务直通（跳过规划审查，单执行者+验收） |
| `human_checkpoints` | `false` | `true` = 计划审完暂停，带决策清单等人工拍板 |
| `max_fix_rounds` | `5` | 验收 fail 后修复循环上限（1-10） |
| `tier` | `medium` | 仅 quick 模式：执行者档位 |

## 定制（fork）

脚本内所有可定制位置都有 `[FORK]` 注释标记：

1. 模型分派表（换模型 / 加档位）
2. `.planning/` 目录约定（换落盘路径与文件名）
3. 修复工程师档位
4. 依赖并行策略（按批屏障 / 失败不拦下游——这两点是当前行为，fork 高频修改点）

复杂项目：复制本文件改名（避免同名抢占触发词）→ 按注释逐处适配 → 改 frontmatter 的 description / whenToUse。

## 已知局限（诚实清单）

- v1 只完整跑过一次（任务：让工作流给自己写 fork 适配指南），执行与验收质量尚可，但暴露过**文档类任务被拆成 5 个串行 agent** 的过度编排问题——已内置拆分守则（任务数最少化、同文件任务禁排 3+ 串行长链），尚待更多项目验证
- 验收依赖 Opus 亲跑命令核对，成本较高；小任务请用 `mode=quick`
- 非 git 仓库会自动降级：规划师记录不到基线 commit 时，以文件快照（行数/字节）做增量基准
- 依赖成环时兜底为全并行；依赖任务失败不会自动拦停下游
